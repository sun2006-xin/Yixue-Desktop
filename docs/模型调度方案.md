# 译学助手模型调度方案

版本：v0.1
日期：2026-09-08
目标：在保证核心质量的前提下，减少不必要的高能力模型消耗。

## 1. 总原则

本项目不按“所有事情都用最强模型”执行，而按任务风险调度：

```text
明确规格/架构风险 → GPT-5.6 Sol
普通实现/中等复杂度 → GPT-5.6 Terra
机械改动/高频检查 → GPT-5.6 Luna 或 5.4-mini
极少数重大阻塞/安全升级审查 → GPT-6 Astra
```

5.6-sol 作为主开发模型是合理的：官方将其定位为复杂专业工作和编码的旗舰模型；Terra 用于智能与成本平衡，Luna 用于成本敏感的高频任务。具体可用性和实际额度以当前 Codex 账户为准。

## 2. 明确分工

### 2.1 GPT-5.6 Sol：核心工程模型

默认用于以下任务：

- Rust Core 架构和领域模型。
- Flutter 与 Rust FFI 边界设计。
- SQLite schema、迁移和数据一致性。
- TranslationProvider、模型路由和本地推理集成。
- OCR/ASR/文章解析等跨模块功能。
- 隐私、权限、密钥存储和文件安全。
- 性能瓶颈、并发、任务取消和数据竞争问题。
- 多文件但有清晰规格的核心功能。
- 失败两次以上的根因分析。
- 发布前的核心集成和回归修复。

不要求 5.6-sol 处理：批量改名、简单文档排版、重复测试样例、简单 CSS 数值调整等机械任务。

### 2.2 GPT-5.6 Terra：平衡模型

用于：

- 已有明确接口的普通功能实现。
- Flutter 页面组件和状态管理。
- 中等复杂度的单模块测试。
- API 适配器、导入导出、历史记录等常规功能。
- 代码可读性重构，但不改变核心行为。
- 对 Sol 已完成代码做第二轮普通审查。

### 2.3 GPT-5.6 Luna：高频低风险模型

用于：

- 生成基础测试样例和 fixture。
- 文档整理、注释、变更日志。
- 简单 UI 文案和字段映射。
- 已验证逻辑的机械重构。
- 格式化、静态检查结果归类。
- 将已有设计转换为简单页面骨架。

Luna 不负责：架构决定、数据库迁移、权限安全、模型接入、性能根因和最终发布判断。

### 2.4 GPT-5.4-mini：可选的机械执行模型

仅在当前环境可用且任务非常简单时使用：

- 单文件小改动。
- 简单测试补齐。
- 文档索引和格式转换。
- 不涉及业务判断的重复性工作。

如果任务描述中出现“可能影响数据/协议/安全/跨平台”，不得交给 5.4-mini。

### 2.5 GPT-6 Astra：升级闸门，不作为默认模型

当前项目不需要常态使用 GPT-6 Astra。只有满足以下任一条件才考虑升级：

1. Sol 在两个独立尝试后仍无法定位核心阻塞。
2. 需要对复杂安全边界、隐私泄露风险或供应链风险做高强度审查。
3. Windows、Android、iOS 三端出现难以归因的交叉平台问题。
4. 需要对最终架构做一次独立的高风险反方审查。

升级前必须先保存失败证据、当前 diff、测试输出和已尝试方案；不允许用 Astra 重新盲写整个项目。

## 3. 项目阶段调度

| 阶段 | 主要工作 | 默认模型 | 低价模型可做 | 不可委托给低价模型 |
|---|---|---|---|---|
| P0 | 规格、目录、验收基线 | Sol | 文档整理 | 核心边界决策 |
| P1 | Rust Core、领域对象、SQLite | Sol | 测试 fixture | schema、迁移、一致性 |
| P2 | FFI、Flutter/Rust 接口 | Sol | 样板页面 | FFI 所有权、线程和错误边界 |
| P3 | 本地模型、CTranslate2、Provider | Sol | 文档与基准脚本 | 模型加载、量化、隐私和路由 |
| P4 | 快速翻译和学习页面 | Sol/Terra | UI 样式、测试 | 任务状态、数据保存、判题规则 |
| P5 | 文章、OCR、截图 | Sol/Terra | fixture、文案 | 文件安全、取消、长文任务 |
| P6 | Android/iOS 最小壳 | Sol | 页面复制和资源整理 | 平台权限、模型路径、生命周期 |
| P7 | 性能、隐私、发布 | Sol | 报告整理 | 最终 PASS/FAIL、发布结论 |

## 4. 每次调用的任务包

给任何模型的任务必须包含：

1. 当前阶段和目标。
2. 允许修改的文件范围。
3. 不允许改变的接口和行为。
4. 验收标准。
5. 验证命令。
6. 当前失败输出或相关证据。

模型不得自行扩大范围。若发现架构问题，应先报告并暂停实现，不得顺手重写无关模块。

## 5. 交接规则

### Sol → Terra/Luna

只有在以下条件全部满足时才交给低价模型：

- 接口已固定。
- 行为已有测试或明确样例。
- 低价模型只做局部、可回滚修改。
- 修改后由当前主流程运行验证。

### Terra/Luna → Sol

出现以下情况立即升级：

- 测试失败且原因不明显。
- 需要改数据库或公共接口。
- 出现跨平台差异。
- 修改涉及权限、隐私、密钥、模型文件或用户数据。
- 低价模型连续两次修复不稳定。

## 6. 验证规则

模型级别不等于质量证明。无论由哪个模型完成，都必须由当前工作区重新验证：

- Rust：`cargo fmt --check`、`cargo test`、必要时 `cargo clippy -- -D warnings`。
- Flutter：`dart format --output=none --set-exit-if-changed .`、`flutter analyze`、`flutter test`。
- 集成：本地翻译、离线运行、导入文章、学习记录、模型切换和错误恢复。
- 性能：启动时间、内存、页面切换、滚动帧率、翻译队列和模型加载。
- 隐私：日志扫描、API 密钥扫描、网络请求边界和数据导出/删除。

任何模型都不能用“代码看起来正确”替代命令验证。

## 7. 当前推荐使用方式

你切换到 GPT-5.6 Sol 后，先让它只完成 P0/P1：

1. 阅读本文件和《产品与技术框架.md》。
2. 创建 Flutter + Rust Core 的多包目录。
3. 先定义 Rust Core 的领域对象、Provider 接口、SQLite schema 和最小测试。
4. 暂不写完整页面、OCR、视频和所有学习功能。
5. 通过 Core 测试后，再进入 FFI 和 Flutter 首页。

本方案不修改当前 Codex 的模型配置；模型切换由用户在 Codex 界面或任务级设置中完成。

## 8. 翻译模型实验阶段

快速翻译的 API 调用、结果展示和本地历史闭环完成后，立即进入模型实验，不等五大功能全部完成。

第一轮以本地模型为主，只做可重复基准，不调用付费 API，也不立刻训练：

1. 先完成本地模型目录登记、包结构/哈希/许可证校验和 CTranslate2 运行时探测；未校验模型不得启用。
2. 固定一组不含隐私的英汉样例，覆盖日常表达、长难句、科技文章、论文摘要、术语、歧义句和格式保留。
3. 第一工程候选固定为两套 OPUS-MT 方向模型：`opus-mt-en-zh` 与 `opus-mt-zh-en`；
   M2M100 418M INT8 是双向质量挑战者，不默认随软件安装。统一记录译意准确、目标语言自然度、
   术语一致、遗漏错译、总耗时、峰值内存和模型体积。
4. API 只作为用户主动配置的可选对照；不配置 API 也能完成全部核心实验，且本地失败时绝不静默转远程。
5. 结果和人工评分只保存在本地。格式保护已经在翻译服务层完成；模型目录与历史数据必须放在稳定的数据目录，不能随预览版本漂移。确认稳定错误类型后，建立有授权的小规模训练集，先做轻量微调，再与未微调基线盲测；没有可复现提升就不发布自有模型。
6. 每个发布模型固定来源、许可证、数据说明、转换器版本、SHA-256 和评测报告；拒绝执行来源不明的模型代码。

### 8.1 首轮实验结论（2026-09-11）

固定 16 例双向基准已完成。双向 OPUS-MT INT8 的平均延迟为 177.06 ms、P95 为 490 ms、
峰值工作集为 138.27 MiB；M2M100 418M INT8 分别为 468.56 ms、1310 ms 和 850.51 MiB。
M2M100 虽减少了个别漏译，但出现繁体混入和更严重的技术术语错译，质量提升不足以抵消
约 2.65 倍平均延迟、约 6.15 倍峰值内存和更大的模型包。

因此预览版继续以 OPUS-MT 为默认双向翻译基线，M2M100 不接入应用、不随安装包分发。
下一实验阶段先扩充有授权、去隐私的数据与盲评集，再对 OPUS-MT 做轻量微调；不从零训练模型，
也不根据 16 个样例直接宣布质量提升。完整报告见
`benchmarks/results/opus-vs-m2m100-418m-int8-20260911.md`。

授权数据规范、64 条扩展固定集、数据泄漏校验器、双盲工具和 OPUS-MT v2 基线已完成。
格式保护已在翻译服务层完成，并通过真实双向链路 16/16 验证；漏译、术语和论文表达再进入
与固定集隔离的训练数据。API 连通性测试继续延后，且不影响完全离线的默认使用路径。

### 8.2 关于“从零训练全能模型”的决策边界

如果后续固定集和人工盲评持续证明现有专用模型无法满足核心场景，可以立项训练“译学”模型；
但“从零训练”仍是远期备选，不作为当前预览版的直接补救。优先顺序是：先选择已有多语言预训练底座，
再用有授权、去隐私、与评测集隔离的数据进行微调、蒸馏或术语适配。只有在底座许可、数据规模、
算力预算、跨语言覆盖和长期评测门槛都满足时，才评估从零预训练。翻译、总结/解释、ASR、TTS
仍保持分模型角色；“全能模型”只能作为用户可选的统一入口，不能绕过每个角色的能力验证。

### 8.3 试译与评测必须服从模型方向

- 模型包完成校验后，试译和固定集评测必须读取包内源语言/目标语言，并只选择同方向样例；禁止用一条固定英译中句子测试所有模型。
- 运行时路径必须以发布包结构为准，不能把开发环境的 `runtime/install/.../bin` 路径写入桌面预览逻辑。
- 方向一致和进程可调用只属于链路门禁；术语准确、学术表达、语义完整和人工盲评仍是质量门禁，任何一项不足都不能宣称正式工作级翻译。

### 8.4 评测结果必须可对照且不夸大结论

- 固定集样例的参考译文必须随评测结果返回到模型页，用户应能同时看到原文、模型译文和参考译文。
- `referenceMatch` 只代表规范化字符串是否完全一致，不能作为语义、术语、语气或论文表达的自动评分；界面必须明确“仅供人工对照”。
- 本地和远程评测必须共用目标语言质量门禁，至少拦截空结果、疑似重复、原文未翻译、元话术和格式保护损坏。
- 评测不得写入快速翻译历史或修改当前 Provider。评测通过仅表示当前样例通过链路/基础输出筛选，正式工作级结论仍需要隔离测试集和人工盲评。

### 8.5 模型目录必须绑定语言方向

- 本地模型目录记录 `source_language` 与 `target_language`；两者必须同时存在，值统一保存为小写语言代码。
- 快速翻译选择本地模型时，优先要求目录方向与请求方向完全一致；已知方向不一致的模型必须跳过，不能因为路径或名称相似而猜测。
- 旧版本目录没有方向信息时继续可用，但只能作为兼容候选；用户一旦重新校验或登记模型，应补齐方向元数据。
- 模型与服务页必须区分“已发现”“已校验”“已配置”“当前使用”四种状态。扫描到模型不等于它已经接管翻译。
- 方向门禁解决的是路由正确性，不解决语义准确性。术语、漏译、自然度、学术表达和格式保护必须继续由固定集、人工盲评和授权数据实验验证。

### 8.6 API 稳定性不是翻译质量门禁

- OpenAI 兼容接口只对 408、409、425、429、500、502、503、504 以及临时网络/超时错误最多重试一次；401、400、模型不存在和响应格式错误立即返回，避免反复发送错误请求。
- 请求默认低随机度，并明确要求只返回译文、保留数字/标点/段落结构；这是可复现性和输出边界控制，不是对模型语义能力的承诺。
- 快速翻译取消在途请求时必须优先结束，不应因重试机制重新发起已取消的请求；本地模型仍以独立进程取消边界为准。
- 语义质量仍按 8.4 和 8.5 执行：固定集只筛选，授权数据与评测集隔离，人工盲评确认漏译/术语/自然度，再决定术语适配、候选模型或轻量微调。
