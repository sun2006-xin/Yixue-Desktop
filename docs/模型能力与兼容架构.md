# 译学模型能力与兼容架构

状态：已确认，作为后续本地模型、用户模型与 API 接入的统一边界。

## 1. 核心原则

译学不把所有能力塞进一个模型，也不按“每增加一种语言就重写软件”的方式扩展。软件只依赖稳定的能力接口，具体模型可以独立安装、替换和升级。

```text
译学页面与任务
  └── 能力路由
      ├── 翻译：专用翻译模型 / 通用大模型 / 用户 API
      ├── 理解：总结、解释、问答、润色、学习反馈
      ├── 听：本地语音识别 ASR
      └── 说：本地语音合成 TTS
```

默认行为必须本地优先。远程 API 仅在用户明确配置和选择后调用，不能在本地模型失败时静默上传内容。

## 2. 多语言扩展路线

### 第一阶段：英汉

- 双向 OPUS-MT 负责快速、稳定、低资源的基础翻译。
- M2M100 418M INT8 作为多语言与质量挑战者。
- 通用本地大模型负责文章总结、语境解释、术语整理和学习反馈，不承担首版每一句基础翻译。

### 第二阶段：常用语言

- 优先验证一个多语言翻译模型覆盖英语、中文、日语、韩语、法语、德语、西班牙语等常用方向。
- 对高频且质量不足的语言方向，允许安装单独的轻量专用模型包。
- 语言、模型和程序分离；增加语言通常只新增经过签名/哈希校验的模型包和语言元数据。

### 第三阶段：译学模型

- 不从随机参数训练通用大模型。
- 在有明确许可证的预训练模型上做微调或参数高效微调。
- 翻译模型优化忠实度、术语一致性和文体；通用模型优化总结、解释和学习反馈，两类训练集与评测分开。
- 只有固定基准和人工盲测证明持续提升时，才发布“译学”微调版本。

## 3. 千问的角色

已有千问可以通过 Ollama 的本地 HTTP 接口接入，适合：

- 文章、字幕和会议内容总结；
- 双语解释、语法分析、例句生成和学习反馈；
- 结合上下文润色专用模型的译文；
- 作为未安装对应专用翻译模型时的显式候选路径。

千问不是专用机器翻译模型，速度、术语稳定性和逐句忠实度必须单独测试，不能因为能生成中文就自动设为默认翻译模型。千问文本模型本身也不等于语音模型；实时听说仍由 ASR 与 TTS 组件完成。

## 4. 用户模型与 API 兼容层

首批适配器固定为：

1. `CTranslate2 Local`：译学官方及用户导入的专用翻译模型包。
2. `Built-in Generative Local`：由译学直接携带运行时，加载官方总结/解释模型，不要求用户安装其他软件。
3. `Ollama/LM Studio Compatible`：只为已经使用这些工具的高级用户提供模型发现与能力测试。
4. `OpenAI Compatible Local`：vLLM 等本机兼容端点。
5. `OpenAI Compatible Remote`：用户自行配置的兼容 API，密钥进入系统安全存储。

模型登记不能等于可用。启用前必须完成：

- 端点和本地路径校验；
- 模型列表或模型标识确认；
- 最小翻译/总结试跑；
- 超时、取消和错误脱敏；
- 能力、语言、上下文长度与本地/远程标识展示；
- 失败时保持原任务，不静默切换远程服务。

无法自动识别的模型允许用户手动声明能力，但界面必须标记“未经验证”，试跑成功后才可用于正式任务。

### 4.1 Provider 角色与实际路由

模型目录中的 `assignedRoles` 只表示“这个模型候选可以承担什么”；用户真正接入的
Provider 另有独立的 `assignedRoles`，表示“本次配置愿意把它用于什么”。两层都保存在本地
 SQLite，当前 schema 为 v9（Provider 角色字段在 v8 引入）；重新扫描模型目录不能覆盖用户已经保存的 Provider 选择。

- 模型页的“设置用途”先更新候选记录；已接入模型的“设置用途”更新 Provider 记录。
- 一个产品角色同一时间只保留一个显式 Provider 分配，切换时移除其他 Provider 的同一角色，
  但不会删除它们的 API 密钥、模型目录或非冲突角色。
- 快速翻译只选择“已启用、显式分配翻译角色、且语言方向匹配”的本地 Provider；远程 Provider
  也遵守同一规则。没有显式角色的旧配置只保留兼容性翻译兜底，新的配置不得依赖这个兜底。
- “当前使用”表示已启用并承担翻译；“已分配”表示已选用途但还没有成为当前翻译 Provider；
  “候选”表示模型目录中可承担该角色，但尚未接入。角色分配本身不会加载权重，也不会偷偷
  启动 Ollama、Python 或其他外部运行时。
- 角色映射只负责选择，不伪造能力。真正执行前仍需经过 Provider 类型、语言方向、运行时、
  超时、取消和输出质量门禁。

## 5. 语音能力

- `ASR`：把麦克风、视频、会议或直播音频转成带时间戳文本。
- 翻译：按稳定片段翻译，保留原文、译文与时间帧。
- `TTS`：朗读单词、句子或译文，支持跟读学习。
- 通用大模型：在会后生成摘要、知识点、行动项和学习材料。

实时链路必须允许分别替换 ASR、翻译、总结和 TTS，避免一个模型加载失败导致整套功能不可用。

## 6. 当前实施顺序

1. 将现有模型包校验能力贯通 Rust FFI 与“模型与服务”页面。
2. 接入 CTranslate2 本地运行时，完成双向 OPUS-MT 的首轮真实翻译。
3. 运行 OPUS-MT 与 M2M100 固定基准，记录质量、延迟、内存和体积。
4. 先验证译学内置生成式运行时；再增加 Ollama 兼容适配器，让已有环境中的千问承担总结与解释试验。
5. 为用户本地模型/API 增加连接检测、模型发现、能力试跑和明确错误提示。
6. 到 AI 同传阶段再接入 ASR/TTS，不提前把语音依赖塞进基础翻译安装包。

## 7. 2026-09-13 Ollama 原生接入边界

- 模型与服务页扫描到 Qwen/Ollama 候选后，提供“配置兼容接口”入口；会预填本机 Ollama 原生地址 `http://127.0.0.1:11434/api`、模型 ID 和免密钥说明，用户仍可修改地址。该入口只保存已有兼容接口，不会自动安装或启动 Ollama，且首次保存默认为未启用，避免未启动的接口截走默认翻译请求。
- 原生 Ollama 使用 `/api/chat` 翻译和 `/api/tags` 连接探测；`/v1` 仍走 OpenAI 兼容协议。仅允许回环地址免密钥，远程地址继续要求密钥并进入系统安全存储。
- 该适配器是对已有本地服务的连接能力，不等于译学已经随包携带 Ollama 运行时；普通用户默认仍使用译学自带的 CTranslate2 翻译包，避免额外安装依赖。
- 本机 Qwen 原生接口已完成一次英中真实回归，但冷启动约 19.5 秒；该结果只证明协议和链路可用，不能证明术语、长文、稳定延迟或正式工作级质量。后续质量门禁必须使用固定集、人工盲评和资源记录。
- 本地 Ollama 翻译请求默认显式限制上下文为 2,048 tokens、批量为 64，避免服务按模型默认大上下文一次性申请数 GiB 内存；这只是普通用户的安全默认值，不等于所有模型都已经兼容，后续可在高级 Provider 设置中由用户调整并先做资源预检。
- 模型与服务页的固定集评测同时支持译学本地运行时和已启用的兼容/API Provider。评测结果只用于本地筛选：输出门禁、格式完整性、耗时和人工参考文本分开呈现，不把“请求成功”包装成翻译准确率。

## 8.7 能力试跑与不兼容说明

模型页的“能力试跑”是接管前的最小验证，不是完整质量评测，也不改变当前 Provider：

- 已校验的译学本地翻译包：读取包内语言方向，使用同方向的一条固定样例，经格式和输出门禁后展示译文、耗时与结果状态。
- 已配置的 API、Ollama 或本地兼容端点：只发送一条用户主动触发的英译中固定样例；不写入历史、不保存请求正文。连接成功不等于模型支持翻译，输出仍需通过空值、原文未翻译、重复异常、元话术和格式门禁。
- 已发现但未配置的模型：只显示兼容说明，不执行权重、模型代码或未知运行时。官方译学包提示“可校验”，Qwen/Ollama 提示“需已有本地接口”，GGUF/Transformers/ONNX 提示“当前版本缺少可安全接管的运行内核”，文件不完整或路径失效提示下一步修复方式。
- 试跑失败必须显示稳定原因（缺少配置、端点不可达、模型不存在、超时、响应格式错误、输出门禁失败或运行时缺失），不自动切换到远程服务。
- 试跑结果仅保留在当前页面会话；长期质量结论仍由固定集、授权数据隔离和人工盲评产生。

实现状态：2026-09-13 已完成统一能力试跑服务、结果弹窗和候选兼容说明；本地/API 两条路径共用输出门禁，质量结论仍未提前放宽。

## 8. 2026-09-14 默认角色与 DeepSeek 兼容边界

- 预览版默认翻译固定走随包的双向 OPUS-MT 派生 CTranslate2 INT8；千问不承担默认逐句翻译，只在用户明确接入并分配“理解与总结”后作为候选。
- “使用 DeepSeek API”是 OpenAI 兼容远程 Provider 的友好预设：官方根地址填写 `https://api.deepseek.com`，客户端追加 `/chat/completions`，模型 ID 由预设填写，密钥由用户提供并进入系统安全存储。保存配置、连接测试和设为翻译仍是三个明确步骤，不因保存就自动接管翻译。
- 外接 API 只在用户配置并显式选择后使用；不提供密钥、不支持模型、超时或质量门禁失败时不会静默切换远程或本地其他模型。真实 DeepSeek 请求需要用户自己的密钥，自动化回归只使用 Mock HTTP，不保存请求正文。
- 首页的“今日总结”当前指本地活动统计，不等于千问生成式总结；文章/字幕/会议的生成式总结接下来复用 `ModelRole.understanding`，单独实现调用、超时、取消、来源和本地保存。

## 9. 2026-09-14 多厂商外接 API 适配策略

- 适配目标是先覆盖市面上大部分主流厂商，而不是把产品绑定到 DeepSeek。第一层做“通用 OpenAI 兼容协议”，凡是厂商公开提供兼容的模型列表与聊天补全端点，就复用同一套连接、取消、超时、输出门禁和角色分配逻辑；每家厂商可以有自己的预设，减少普通用户填写地址、模型 ID 和密钥的负担。
- 首批预设按主流厂商和本地网关的实际需求逐步登记；预设只代表填写帮助，不能把“已显示厂商名称”误写成“已完成真实适配”。当前代码已具备通用兼容入口，DeepSeek 只有一个便捷预设。
- 当前通用适配器使用 `/models` 做无用户正文的连接测试，使用 `/chat/completions` 做翻译请求；本地 Ollama 原生 `/api/tags` 与 `/api/chat` 仍走已明确的独立协议分支。
- 不兼容厂商的自有协议、签名方式、特殊请求体或非聊天补全接口，列入第二层独立适配。每增加一家，新增一个小型客户端适配器，并复用统一的 Provider、密钥、取消、超时、输出门禁、来源显示和错误码接口；不把非兼容服务硬套成兼容服务。
- 通过配置不等于可用：必须经过连接测试和固定样例能力试跑，用户再明确分配翻译、理解与总结等角色。自动化测试只使用 Mock HTTP，不将真实密钥或用户正文写入测试和日志。
